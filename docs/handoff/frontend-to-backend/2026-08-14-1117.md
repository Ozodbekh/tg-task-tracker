# Web panel needs stats, tasks, employees and chats endpoints

The web panel is built and wired to the contract below. Only `auth` exists
today, so every screen is dead until these endpoints land. Nothing in the
frontend holds sample data.

Seed the database with fake rows once the endpoints are up so the UI can be
tested end to end.

## Shared query parameters

Every endpoint in this note except `GET /api/employees` and `GET /api/chats`
accepts the same filter set. All of them are optional except `period`.

- `period` — one of `day`, `week`, `month`, `quarter`, `9months`, `year`, `all`.
  Ranges end now and start `1 / 7 / 30 / 90 / 270 / 365` days back; `all` has no
  lower bound. The range is applied to `tasks.created_at`.
- `bucket` — `hour`, `day`, `week`, `month`. Only `/api/stats/timeseries` uses
  it. Default per period: `day → hour`, `week`/`month` → `day`,
  `quarter → week`, `9months`/`year`/`all` → `month`.
- `status` — `open`, `in_progress`, `done`, `cancelled`.
- `chat_id` — internal `chats.id`.
- `chat_type` — `private` or `group`.
- `employee_id` — internal `employees.id`.

Status and chat filters must apply to every listed endpoint, statistics
included — the panel filters the whole dashboard, not only the task list.

Auth: session cookie, like the rest of the API.

Errors: `400` with `{ "detail": "Invalid filters" }` for an unknown `period`,
`bucket`, `status` or `chat_type`; `404` for an unknown id.

## Shared shapes

`employee`, `chat` — the stored rows as they are in `docs/api/`-style JSON:
`{ id, telegram_id, name, created_at }` and
`{ id, telegram_id, type, title, created_at }`.

`by_status` — `{ open, in_progress, done, cancelled }`, all integers.

`completion_rate` — float `0..1`: `done / (total - cancelled)`, `0` when the
denominator is `0`.

Durations are seconds as float, `null` when there is nothing to average:

- `avg_completion_seconds` — `done_at - created_at` over done tasks.
- `avg_response_seconds` — `started_at - created_at` over tasks that were
  started.

Timestamps are ISO 8601 with timezone.

## GET /api/stats/overview

Headline numbers for the dashboard cards.

```json
{
  "total": 0,
  "by_status": { "open": 0, "in_progress": 0, "done": 0, "cancelled": 0 },
  "completion_rate": 0.0,
  "avg_completion_seconds": null,
  "avg_response_seconds": null,
  "overdue_open": 0,
  "unresolved": 0,
  "active_employees": 0,
  "active_chats": 0,
  "previous": { "total": 0, "done": 0, "completion_rate": 0.0 }
}
```

- `overdue_open` — tasks still `open` older than 3 days.
- `unresolved` — rows in `unresolved_messages` in the same range and chat
  filters.
- `active_employees` / `active_chats` — distinct ids among the matched tasks.
- `previous` — the same window shifted one length back, for the growth badge.
  `null` when `period=all`.

## GET /api/stats/timeseries

The dashboard trend chart. One point per bucket, ascending, empty buckets
included so the line has no gaps.

```json
[{ "bucket": "2026-08-14T00:00:00+05:00", "created": 0, "done": 0, "in_progress": 0, "cancelled": 0 }]
```

`created` counts tasks created in the bucket; the other three count tasks whose
current status is that value, keyed by the same `created_at` bucket.

## GET /api/stats/employees

One row per employee that has at least one task in the range. Sorted by `total`
descending.

```json
[{
  "employee": {},
  "total": 0,
  "by_status": {},
  "completion_rate": 0.0,
  "avg_completion_seconds": null,
  "avg_response_seconds": null,
  "last_activity_at": null
}]
```

`last_activity_at` — the most recent `task_events.created_at` for that employee
in the range, falling back to the newest task `created_at`.

## GET /api/stats/chats

One row per chat with at least one task in the range, sorted by `total`
descending.

```json
[{
  "chat": {},
  "total": 0,
  "by_status": {},
  "completion_rate": 0.0,
  "unresolved": 0,
  "participants": 0,
  "last_task_at": null
}]
```

`participants` — distinct assignees in that chat within the range.
`unresolved` — that chat's rows in `unresolved_messages` within the range.

## GET /api/employees

Every employee, sorted by name. No filters. Used to fill the filter dropdown.

## GET /api/employees/{id}/stats

The same object as one row of `/api/stats/employees`, for the employee page.
`404` when the employee does not exist.

## GET /api/chats

Every chat, sorted by title. No filters. Used to fill the filter dropdown.

## GET /api/tasks

The task list. Filters above, plus:

- `search` — case-insensitive substring of `tasks.text`.
- `page` — 1-based, default `1`.
- `page_size` — default `20`, max `100`.
- `sort` — `created_at`, `-created_at` (default), `done_at`, `-done_at`.

```json
{
  "items": [{
    "id": 0,
    "text": "",
    "status": "open",
    "message_id": 0,
    "message_link": null,
    "employee": {},
    "chat": {},
    "created_at": "",
    "started_at": null,
    "done_at": null,
    "cancelled_at": null
  }],
  "total": 0,
  "page": 1,
  "page_size": 20
}
```

`message_link` — a `t.me` deep link to the original message, or `null` when one
cannot be built. The panel links back to Telegram with it; the frontend must not
have to assemble it from `chat_id` and `message_id`.

`employee` and `chat` come embedded. Do not return bare ids — the list renders
names and would otherwise need a second round trip per row.

## GET /api/tasks/{id}

One task in the shape above, plus its full history, ascending by time:

```json
{ "events": [{ "id": 0, "status": "open", "actor_name": "", "message_id": 0, "text": "", "created_at": "" }] }
```

`actor_name` — the resolved display name of `task_events.actor_id`, not the raw
Telegram id.

`404` when the task does not exist.

## GET /api/unresolved

Messages tagged `#task` whose assignee could not be resolved. Same pagination
envelope as `/api/tasks`. Honors `period`, `chat_id` and `chat_type`; `status`
and `employee_id` do not apply.

```json
{ "items": [{ "id": 0, "chat": {}, "message_id": 0, "message_link": null, "text": "", "created_at": "" }] }
```

## Out of scope

- Deadlines: the panel shows `overdue_open` on a fixed 3-day rule, no deadline
  column anywhere.
- Any write endpoint. The panel is read-only; statuses change in Telegram.
- Per-employee or per-chat CRUD.
- Export and reporting downloads.

## What the frontend does next

Nothing until these ship. Once they are live with seeded data, the panel is
pointed at the API and verified screen by screen; a follow-up note goes out only
if a response shape has to change.
