# Pagination rules for the list endpoints

Amends `2026-08-14-1117.md`. That note stands as written except for the four
points below; read this one after it and build to this shape.

## What changed

1. `GET /api/stats/employees` and `GET /api/stats/chats` no longer return a bare
   array. Both return the same envelope as `/api/tasks`.
2. `page` and `page_size` are accepted by every list endpoint, `/api/unresolved`
   included.
3. `page_size` limits are now stated per endpoint.
4. `GET /api/employees` and `GET /api/chats` stay unpaginated, on purpose.

## The envelope

Every list endpoint returns:

```json
{ "items": [], "total": 0, "page": 1, "page_size": 20 }
```

`total` is the count of rows matching the filters, **before** paging. The panel
draws "N tadan A–B ko'rsatilmoqda" and the page count from it, so it cannot be
the length of `items`.

`page` and `page_size` echo back what was applied, not what was requested. When
`page` is past the end, return an empty `items` with the real `total` — not a
`404`.

## Parameters

- `page` — 1-based, default `1`. `400` on `0` or a negative value.
- `page_size` — default and maximum per endpoint below. A larger value is
  clamped to the maximum rather than rejected.

| Endpoint                | default | max | notes                              |
| ----------------------- | ------- | --- | ---------------------------------- |
| `GET /api/tasks`        | 20      | 100 | panel offers 20 / 50 / 100         |
| `GET /api/stats/employees` | 20   | 100 | sorted by `total` desc             |
| `GET /api/stats/chats`  | 20      | 100 | sorted by `total` desc             |
| `GET /api/unresolved`   | 20      | 100 | sorted by `created_at` desc        |

Sorting must be stable across pages — add `id` as the final tie-breaker, or the
same row shows up on two pages.

## Where the panel uses small pages

The dashboard asks the two stats endpoints for `page=1&page_size=8` and the
chats screen for `page=1&page_size=10`, purely to draw the top-N charts. This is
the same endpoint, not a separate one: the sort is what makes it a top-N, so
`total` desc ordering has to be reliable.

## Unpaginated on purpose

`GET /api/employees` and `GET /api/chats` fill the filter dropdowns and must
return every row in one response, sorted by name and title. Do not add paging to
them; a paginated dropdown would silently hide options.

## Counts that must not come from a page

The chats screen reads `active_chats`, `unresolved` and `total` from
`GET /api/stats/overview`, because summing a single page would understate them.
Overview must therefore respect the same filters, which the previous note
already requires.

## Out of scope

- Cursor or keyset pagination. Offset paging is enough at this data size.
- A `has_next` flag; `total` and `page_size` already give it.
