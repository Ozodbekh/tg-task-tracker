# Two new task statuses: on_hold and blocked

The assignee can now park a task from Telegram, so `TaskStatus` has two more
values. The task list, the status filter and every `by_status` object carry
them. Anything that switches on the four old values needs a branch for the two
new ones, or it will fall through.

## New statuses

- `on_hold` — the assignee paused it themselves, tag `#onhold`
- `blocked` — the assignee is waiting on someone else, tag `#blocked`

`#cancel` is new too, but it lands on the existing `cancelled`; nothing changes
for you there.

## What changed in the contract

- `status` query parameter accepts `on_hold` and `blocked` — see
  [filters](../../api/filters.md)
- `by_status` is now `{ open, in_progress, on_hold, blocked, done, cancelled }`,
  six keys instead of four — see [filters](../../api/filters.md#shared-shapes)
  and [stats](../../api/stats.md)
- `completion_rate` is unchanged: `done / (total - cancelled)`. `on_hold` and
  `blocked` stay in the denominator, so parking work lowers the rate.

## What did not change

`GET /api/stats/timeseries` still returns `created`, `done`, `in_progress` and
`cancelled` per bucket. There is no `on_hold` or `blocked` series. Say so if the
trend chart needs one.

Neither status stamps a column on the task row, so `started_at`, `done_at` and
`cancelled_at` stay `null` for them. The moment a task was parked is in its
history, through `GET /api/tasks/{id}` → `events[]`, together with the comment
the assignee sent along with the tag.

## Seeded data

`make seed` now produces both statuses, roughly 7% `on_hold` and 5% `blocked`,
so the screens have something to render.

## Out of scope

- A timeseries series per new status
- Any write endpoint. Statuses still change in Telegram only.
